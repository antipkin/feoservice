# 📄 Спецификация продукта: ФЭО-Сервис (v1.1)

**Дата актуализации:** 25 сентября 2026 г.  
**Статус:** MVP (Phase 1)  
**Цель:** Создание веб-приложения для планирования ФЭО тарифа и учёта выполненных работ для МКД и паркингов с двойным учётом (деньги + количество услуг).

---

## 1. 🎯 Видение и ключевые принципы

1. **Двойной учёт:** Каждая операция (план и факт) всегда содержит: `количество` (натуральные единицы: м², шт, пог.м) и `сумму` (рубли).
2. **Ресурсная модель:** Тариф формируется не просто из стоимости услуги, а из: `Услуга` → `Норматив ресурса` → `Стоимость ресурса`.
3. **Объекты:** Поддержка двух типов объектов: МКД (расчёт на м²) и Паркинги (расчёт на машиноместо).
4. **Простота ввода:** Интерфейс должен позволять быстро копировать план в факт и редактировать только отклонения.

---

## 2. 🏗️ Технологический стек

### 2.1. Разработка
* **Frontend:** Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui.
* **Backend:** Python FastAPI + Pydantic для валидации.
* **Database:** PostgreSQL 16 (через SQLAlchemy + asyncpg) — стабильная версия с поддержкой до ноября 2028.
* **Миграции:** Alembic (async-режим).
* **Документы:** Генерация PDF через backend-библиотеки (WeasyPrint / ReportLab).
* **Контейнеризация:** Docker + Docker Compose.
* **IDE:** Visual Studio Code.
* **VCS:** Git.

### 2.2. Продакшен (Deploy)
* **Сервер:** VPS на базе Ubuntu 22.04/24.04 LTS.
* **Reverse Proxy:** Nginx.
* **SSL:** Let's Encrypt (Certbot).
* **Автозапуск:** Docker Compose с `restart: always`.
* **Путь размещения:** `/opt/feoservice` или `~/feoservice`.

## 3. 🗄️ Модель данных (Core Schema)

### 3.1. Справочники (НСИ)

| Таблица | Поля | Примечания |
|---|---|---|
| **`Object`** | id, name, type ('MKD' \| 'PARKING'), address, area_sqm (для МКД), spaces_count (для паркингов), is_active | Объекты обслуживания |
| **`ServiceType`** | id, code, name, unit (м², шт, пог.м), category | Виды услуг/работ |
| **`Resource`** | id, code, name, unit, type ('material' \| 'labor' \| 'equipment') | Ресурсы (материалы, труд, техника) |
| **`ServiceRate`** | id, service_type_id, price_per_unit, valid_from, valid_to | Расценки на услуги (с историей) |
| **`ResourceRate`** | id, resource_id, price_per_unit, valid_from, valid_to | Расценки на ресурсы (с историей) |
| **`ResourceNorm`** | id, service_type_id, resource_id, quantity_per_unit | Норматив расхода ресурса на 1 ед. услуги |

### 3.2. Планирование

| Таблица | Поля | Примечания |
|---|---|---|
| **`PlanHeader`** | id, object_id, year, status ('draft' \| 'approved'), created_at | Заголовок плана |
| **`PlanItem`** | id, plan_header_id, service_type_id, total_quantity, unit_price, total_amount (вычисляемое) | Позиция плана |
| **`PlanResource`** | id, plan_item_id, resource_id, required_quantity, unit_price, total_amount | Потребность в ресурсах |

### 3.3. Факт и Акты

| Таблица | Поля | Примечания |
|---|---|---|
| **`FactHeader`** | id, object_id, year, month, status ('draft' \| 'approved'), created_by | Заголовок факта |
| **`FactItem`** | id, fact_header_id, plan_item_id (опционально), service_type_id, actual_quantity, unit_price, actual_amount, notes | Позиция факта |
| **`Act`** | id, fact_header_id, act_number, act_date, total_amount, pdf_url | Акт выполненных работ |

### 3.4. Важные правила моделирования
- Для денежных сумм и количеств использовать `Numeric(15,4)` (НЕ Float!).
- Для статусов и типов использовать `Enum`.
- Foreign Keys: `ondelete="CASCADE"` для зависимых записей (PlanItem → PlanHeader), `ondelete="RESTRICT"` для справочников.
- Индексы на часто используемых полях (object_id, year, month, status).

## 4. 👥 Роли и пользовательские сценарии (User Flows)

| Роль | Сценарий |
|---|---|
| **Экономист** | 1. Заходит в "Справочники", добавляет новую услугу и её расценку.<br>2. Создаёт "План на 2027 год" для МКД "Ленина 1".<br>3. Добавляет позиции плана (услуга + кол-во). Система автоматически считает сумму и потребность в ресурсах.<br>4. Нажимает "Рассчитать тариф", получает ₽/м². Утверждает план. |
| **Диспетчер / Мастер** | 1. Открывает "Ввод факта" за текущий месяц.<br>2. Видит список плановых услуг.<br>3. Нажимает "Заполнить из плана", корректирует фактическое количество.<br>4. Сохраняет и отправляет на согласование. |
| **Руководитель** | 1. Видит уведомление о новом факте.<br>2. Сравнивает план и факт в таблице отклонений.<br>3. Нажимает "Сформировать Акт", скачивает PDF, меняет статус на "Утверждено". |

## 6. 🤖 Правила вайб-кодинга (Инструкция для ИИ)

1. **Контекст:** При каждом запросе на генерацию кода я буду ссылаться на этот файл (`SPEC.md`). Ты должен соблюдать двойной учёт (количество + деньги).
2. **Итеративность:** Мы делаем по одной фиче за раз. Не пиши весь код приложения сразу. Сначала схема БД → потом API → потом UI компонент.
3. **Стиль кода:**
   * **Frontend:** Функциональные компоненты React, TypeScript, Tailwind, строгая типизация.
   * **Backend:** Чистые эндпоинты, использование схем Pydantic для валидации входящих данных.
4. **Обработка ошибок:** Если я прошу что-то сделать, а в спецификации есть противоречие или нехватка данных, **спроси меня** перед генерацией кода.
5. **Вычисления:** Все расчёты сумм (`quantity * price`) должны дублироваться: на фронтенде для мгновенного отклика (optimistic UI) и на бэкенде для валидации и сохранения.
6. **Версионность:** Использовать именно `postgres:16` в Docker-образах (не `latest`).
